# סטורי 7.3 — כוונון ה־state בצד הלקוח (TanStack Query): מה השתנה ולמה

<div dir="rtl" style="direction: rtl; text-align: right;">

## הבעיה

ל־TanStack Query יש `staleTime` של 0 כברירת מחדל: כל נתון נחשב "ישן" מיד אחרי שהגיע. לכן כל כניסה למסך וכל חזרה לחלון שלחו שוב בקשה לשרת (למשל `GET /api/tags`), גם כשאף אחד לא שינה כלום.

רענון אחרי עריכה כבר היה קיים מאפיק 4: כל כתיבה עוברת דרך `invalidationMap` ומרעננת את מה שהשתנה. זה לא השתנה.

## הכלל: אחד, במקום אחד

ב־`createAppQueryClient` (`apps/web/src/app/app-providers.tsx`) ברירת המחדל היא עכשיו `staleTime: Infinity`, לכל הנתונים מהשרת.

- נתון נטען פעם אחת, ומשם כל מסך קורא אותו מהזיכרון, בלי בקשה נוספת.
- ברגע שכותבים משהו באפליקציה, `invalidationMap` מסמן את מה שהשתנה, והוא נטען מחדש מיד.

אנלוגיה מ־Angular: זה כמו `shareReplay(1)` על ה־HTTP observable. הבקשה יוצאת פעם אחת וכל מי שנרשם מקבל את אותה תוצאה. ההבדל: כאן אחרי כל עריכה "מאפסים" את ה־shareReplay והבקשה יוצאת שוב.

אין יותר קובץ `query-policy.ts` ואין הגדרות שונות לכל סוג נתון. המסכים משתמשים באפשרויות שנוצרות אוטומטית (`tagsListTagsOptions()` וכו') כמו קודם.

## ההחלטה של עדי (2026-11-08)

שינויים של עורך אחר לא מעניינים אותנו בזמן אמת: הם יופיעו אחרי רענון של הדף. לכן אין צורך בחלון זמן (כמו "דקה") למתכונים.

## בדיקות

`apps/web/src/app/query-caching.spec.tsx` (Vitest + MSW):
- עובר בין מסכים: ספרייה, תגיות, מתכון חדש, חזרה לספרייה, ואז יציאה וחזרה לחלון. מוודא שנשלחה **בקשה אחת בלבד** ל־`/api/tags`, ושאחרי `invalidationMap.tagWrite` נשלחה בקשה שנייה.
- מוודא שברירת המחדל של ה־QueryClient של האפליקציה היא `staleTime: Infinity`.

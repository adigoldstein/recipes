# Bite & Board — PRD Addendum

Technical context carried over from the original `docs/prd.md`. These are **inputs for the architecture step** (`bmad-architecture`), not product requirements. Anything marked _proposed_ still needs Adi's decision there (CLAUDE.md: no architecture decisions without Adi).

## Tech stack (from the original PRD)

- **Monorepo:** Nx (integrated workspace). _Already in place._
- **Frontend:** React, Vite, TypeScript, Tailwind CSS, shadcn/ui, TanStack Query, Zod. _React + Vite in place; the rest proposed._
- **UI state:** React hooks / Context; adopt Zustand only if client state gets complex. _Proposed._
- **Backend:** Python 3.12, FastAPI, Pydantic v2, SQLModel (SQLAlchemy 2), Alembic, Uvicorn, SQLite. _FastAPI app scaffolded with `@nxlv/python` + `uv`; dependencies installed._
- **AI (post-MVP):** `instructor` with OpenAI / Anthropic SDKs or Ollama, behind a Python `Protocol` so providers can be swapped by environment variable.
- **DevOps:** Docker, multi-stage Dockerfiles, Docker Compose.

## Proposed monorepo layout

```
apps/
  web/              React + Vite app (smart/container components, routes)
  recipe-service/   FastAPI core backend (CRUD + domain logic)
  ai-service/       optional later split for AI work
libs/
  ui-components/    presentational components (props in, callbacks out, tokens only)
  data-access/      API client, TanStack Query hooks, Zod schemas
  shared-types/     TypeScript types generated from the FastAPI OpenAPI schema
docker/             Dockerfiles
docker-compose.yml
```

Decided: shared libraries live under `libs/` (Adi, 2026-10-26).

## Component and state approach (original PRD)

- **Presentational components** (`libs/ui-components`): no API calls, no server/global state; data via props, events via callbacks. Examples: `RecipeCard`, `IngredientList`, `PortionSelector`, `SearchBar`, `ModalLayout`.
- **Container components** (`apps/web`): side effects, server state, routing. Examples: `RecipeDashboardContainer`, `RecipeDetailsView`.
- **Server state:** TanStack Query only. **UI state:** hooks/Context.

## Draft data model (original PRD, updated for the new requirements)

- **Recipe:** id, title, description?, category, base_servings, prep_time_minutes?, cook_time_minutes?, created_at, updated_at.
- **Ingredient:** id, recipe_id, position, name, amount? (null = to taste), unit?, note?, **original_amount?**, **original_unit?** (set on first change — FR-7).
- **InstructionStep:** id, recipe_id, step_number, description.

Changes vs. the original: prep/cook time optional; amount optional (to-taste); explicit ingredient position; original-value fields; ID type to be decided in architecture (UUID vs. integer).

## Technical decision points to settle in architecture

1. UI state: Context vs. Zustand (original default: Context first).
2. Single FastAPI app vs. a separate `ai-service` (original default: single app, modular folders).
3. LLM provider abstraction (post-MVP).
4. ID strategy, API shape for nested ingredients/steps (replace-all vs. per-item endpoints), migration workflow.
5. Where scaling/rounding logic lives (pure TS function in a lib, unit-tested).
6. Auth: JWT storage in the browser (memory + refresh vs. httpOnly cookie vs. localStorage), password-hashing library (e.g. argon2 / bcrypt), rate-limiting approach.

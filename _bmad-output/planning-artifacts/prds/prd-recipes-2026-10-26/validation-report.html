Bite & Board — Validation Report

docs/prd.md
Poor

This document is a technical design sketch with a PRD title. It does three things well: the stack, the deferred decisions with their fallbacks, and three feature mechanics (scaling formula, consolidation key, AI import pipeline). As a product requirements source it is thin to broken. It has no stated user or problem, no FR IDs or acceptance conditions, no success criteria, and no non-goals. Several features appear in the milestones but are never specified (Smart Ingredient Substitution, recipe edit/delete, search, menu persistence). For a personal hobby project the light rigor is fine. But the PRD is meant to feed UX, architecture, and epics/stories, and those workflows will have to invent most of the product behavior themselves unless the done-ness and scope gaps are closed first.

The adversarial reviewer agrees on the core gaps (no user, no FRs, incomplete CRUD) and reaches the same bottom line: not ready for downstream work. It adds risks the rubric did not raise. Server-side URL import is an unspecified fetcher with an SSRF surface, and schema.org JSON-LD is ignored as a cheaper path. A deployed instance with no auth exposes the paid LLM endpoint. There are no NFRs, most importantly phone-width use in the kitchen and LLM latency/cost bounds. Scaling has no rounding, display, or "to taste" rules. Phase 2 has no app shell, routing, or list/detail screens. There is no test strategy. It also flags two technical consistency hazards: Zod schemas written separately from the OpenAPI types, and the risk of two services writing to one SQLite file.

Decision-readiness

adequate

The "Key Decision Points" block at the top of the doc is the strongest part of the PRD. Each item is stated as a decision or an explicit deferral, with a default and a trigger. Item 4 is closed (@nxlv/python with uv). A reader who pushes back on Zustand or the service split finds the objection already handled.

What is missing is product decisions. Every listed decision is technical. Product-level choices with real trade-offs are not surfaced, so they will be made silently downstream: AI-import review-before-save, whether event menus are persisted, single-user vs. multi-user, and how far ingredient matching goes. The trigger for the service split ("if/when … warrant it") is also unmeasurable.

Adversarial review

review-adversarial-general.md

Not ready for downstream work. This is a tech-stack memo with a feature sketch attached, not a PRD. It says almost nothing about who uses the product, what they need to do, or how anyone checks that a requirement is met, while it locks in libraries, folder layouts, and component patterns. UX gets no user flows. Architecture gets decisions already made but no quality attributes to test them against. Epics/stories get checklist items with no acceptance criteria and no FR IDs to trace back to. The core recipe loop is barely specified. The three feature areas that make this more than a CRUD app each leave out the edge cases that decide their design.

Counts: 2 critical, 10 high, 10 medium, 4 low (26 total). Severity was added at the caller's request; the adversarial lens does not assign it natively.

critical

F1. No problem statement, users, goals, or testable requirements

general; §1
The "vision" lists capabilities and then moves straight to "Clean Architecture". There is no persona, no JTBD, no success criteria, no FRs, no acceptance criteria, and no out-of-scope list. Epics/stories will be invented by whoever writes them, and "done" will mean "the checkbox is ticked".
Fix: Add Problem & Users, Goals & Success Criteria, numbered FRs with acceptance criteria (e.g. FR-SCALE-1), Non-Goals, and NFRs.
critical

F2. Core recipe lifecycle is incomplete: no update, delete, or browse/detail/create UI

§6 Phase 1 "CRUD endpoints"; §6 Phase 2; §4 updated_at
The section is labeled "CRUD" but has only Create and Read, even though updated_at exists. Zod validates a form that is never specified. The user can't fix a typo or a bad AI import, so every import mistake becomes permanent.
Fix: Add FRs and endpoints for list, detail, create, edit, and delete (with cascade), plus the Phase 2 UI: list, detail, and an editor with dynamic rows.
high

F3. "Smart Ingredient Substitution" appears from nowhere

§6 Phase 3
A whole AI feature shows up as a single checklist line, with no inputs, outputs, UI, or persistence. It is scope creep with no definition.
Fix: Cut it to Non-Goals/Future, or give it a §5.4 spec (trigger, inputs, output shape, suggest vs mutate, UI surface).
high

F4. AI import accepts URLs, but fetching and scraping is unspecified

§5.3 "raw text or a recipe URL"
Nothing covers who fetches, JS-rendered pages, paywalls, timeouts, or token limits. Server-side fetching is an SSRF surface. schema.org JSON-LD is ignored. As written, the URL half of the headline feature cannot be designed.
Fix: Split the requirement into FR-IMPORT-TEXT and FR-IMPORT-URL. For URL import: a fetch with timeout and size cap, http(s) only, private IPs blocked, JSON-LD first with LLM fallback, and a defined error for each failure class. Alternatively, scope the MVP to pasted text only.
high

F5. AI output goes straight into the database with no review step

§5.3 "Direct ingestion into SQLite"; §6 Phase 3
Output that passes Pydantic can still be hallucinated. Bad data gets into the DB silently and spreads into scaling and shopping lists, and with no edit endpoint it can't be fixed.
Fix: Return a draft that the user edits in the recipe editor and saves explicitly. Define behavior after N instructor retries, and store source_url/source_text.
high

F6. Shopping-list consolidation rule is too naive to give correct lists

§5.2 "matching name and unit"
"Egg"/"eggs"/"large eggs", "g"/"grams", and 500 g + 1 kg all fail to merge, and notes is ignored. The headline event feature produces wrong lines, and a later fix needs a data migration.
Fix: Use a canonical unit enum with aliases and a name-normalization rule. Decide on unit conversion. Define how non-mergeable items appear, and add acceptance examples.
high

F7. Event menu has no data model, no persistence, and no scaling rule

§5.2; §3 "active event shopping cart"; §4
There is no Event entity, and client-state "cart" data is lost on refresh. Nothing defines per-recipe servings, how scaling feeds aggregation, or list check-off/export. Architecture can't decide whether this is a backend feature or client-only.
Fix: Decide between a persisted Event and an ephemeral session. Define the pipeline scale → normalize → aggregate. Add FRs for list output, or declare it a non-goal.
high

F8. Scaling ignores rounding, display, and unscalable ingredients

§5.1; §4 amount: float
Scaling produces 1.25 eggs and 0.333 tbsp, and "to taste" has no float amount. Target servings are unbounded, and nothing says whether step text gets scaled. The result is nonsensical quantities exactly where the user looks while cooking.
Fix: Make amount optional. Set rounding and display rules per unit class and bound target servings (1–100). State that instruction text is not scaled.
high

F9. No authentication or ownership model, plus optional public deployment

§1 "personal recipes"; §6 Phase 4 deployment
If deployed publicly with no auth, anyone can read, write, delete, and run the paid LLM endpoint at the owner's expense. Retrofitting user_id later means a schema migration.
Fix: State "single user, local-only" or "single user, deployed behind basic auth / proxy auth". Add a rate limit or cap on LLM endpoints.
high

F10. Non-functional requirements are missing

general
Nothing covers mobile/kitchen use, accessibility, LLM latency/cost, backup/export, offline use, or error handling. Architecture will pick defaults and UX will design desktop-first.
Fix: Add hobby-scale NFRs: phone width ≥ 360px, AI import within 60 s with progress, an LLM spend cap, SQLite backup/JSON export, and WCAG AA contrast.
high

F11. Search and filtering are implied but never required

§3 SearchBar; §4 category
There is no FR for search, filter, or sort, and GET /recipes has no query params or pagination. Components will be built for features with no spec, and the list endpoint contract will churn.
Fix: Add FR-BROWSE (title/ingredient search, category filter, sort). State client-side vs server-side.
high

F12. Phase 2 is missing the screens it depends on, and the phase order has a gap

§6 Phase 2
There is no app shell, routing, list page, or detail page to host PortionSelector, and data-access wiring is in no phase. The first story will turn out to be blocked by unwritten work.
Fix: Order Phase 2 as shell + routing → data-access hooks → list → detail with PortionSelector → editor → event planner.
medium

F13. Implementation details pose as requirements

Key Decision Points; §2; §3
About half the doc is library choices and folder layout. The architecture step becomes rubber-stamping, and the real gaps stay hidden behind detail that looks thorough.
Fix: Move §2–§3 and the key decisions to architecture or to a "Technical Constraints" appendix.
medium

F14. The ai-service is "optional" but drawn as fixed structure

Key Decision 2; §2 layout; §6 Phase 3
"Phase 1/3" is not a decision point, and the split trigger is unmeasurable. This leads to scaffolding drift and empty projects.
Fix: Decide on a single service for MVP, remove ai-service and its Dockerfile from the layout, and record a concrete split trigger.
medium

F15. Several writers sharing one SQLite file is not addressed

§2; §5.3; §6 Phase 4
A split ai-service writing to the same file brings locking problems, and PaaS filesystems are often ephemeral. The result is data loss on the first redeploy or "database is locked" errors.
Fix: Only recipe-service owns the DB. Require a persistent volume, or put hosted deployment out of scope.
medium

F16. Two sources of truth for schemas

§2 libs/data-access Zod vs libs/shared-types generated
Hand-written Zod schemas will drift from Pydantic, so the form will accept input the API rejects.
Fix: Generate Zod from OpenAPI, or make Pydantic authoritative and test Zod against it.
medium

F17. Data model is thin and makes questionable required/optional choices

§4 Recipe, Ingredient
Required times, a free-text single category, no source/image/tags, no ingredient order or grouping, and no base_servings ≥ 1 constraint. AI imports will fail validation, and migrations will churn.
Fix: Make times optional. Add source_url, image or explicit no-images, tags or an enum, position/group, and the constraint.
medium

F18. AI importer's behavior when fields are missing is unspecified

§5.3 Output
Nothing says whether to infer, default, or leave blank for servings, category, and times. A silent "4 servings" breaks scaling, and categories sprawl.
Fix: Set per-field rules (infer-with-flag / default / null), one recipe per import, and a language policy.
medium

F19. LLM provider abstraction hides real differences in capability

Key Decision 3
An env-var swap between Ollama and cloud models assumes equal quality. "Works with GPT" turns into a broken feature on Ollama.
Fix: Set an acceptance bar per provider against a golden set, disable the import UI when no provider is configured, and load keys from env only.
